## 1. 模块目标与范围

M02 首版建议采用两个固定系统角色，不建设动态角色或权限配置：

| `roleCode` | 业务名称 | 门店绑定 | 数据范围 |
|---|---|---|---|
| `ADMIN` | 管理员 | 必须为空 | 可管理全部账号和门店，并按其他模块规则访问全部门店数据 |
| `USER` | 普通用户 | 必须且只能绑定一个启用门店 | 登录后所有门店范围由账号绑定值确定 |

建议的绑定基线：

- 一个门店可以绑定多个普通用户。
- 一个普通用户不能同时属于多个门店，也不能处于“未绑定门店”的可用状态。
- 管理员不绑定“默认门店”，需要门店上下文的管理操作由管理员显式选择门店。
- 普通用户请求中的 `storeId` 不能替代账号绑定值；业务模块从可信的当前账号上下文取得门店。
- 角色只有 `ADMIN`、`USER` 两种固定代码，首版不提供角色新建、删除、改名或权限勾选页面。

本模块包含：

- 管理员创建、查询和编辑管理员或普通用户账户，删除普通用户账户、注销管理员账户，以及重置用户密码。
- 管理员创建、查询、编辑、启停门店，以及物理删除符合安全条件的空门店。
- 固定角色校验，以及普通用户唯一门店的绑定、改绑和数据范围输出。
- 向 M01 提供认证所需的账号状态、密码摘要、角色和门店绑定；向其他模块提供可信的门店范围。

本模块不包含：

- 登录、退出、Redis 会话建立与撤销，以及认证权限集合；这些属于 M01。
- 用户自助注册、找回密码、短信/邮件验证码、第三方登录和多因素认证。
- 动态 RBAC、岗位、部门、区域、多租户或一个账号多门店切换。
- 门店商品、库存、销售和经营数据本身；M02 只提供门店身份与状态。
- 级联删除门店关联的用户、商品、库存、销售、导入或审计数据；普通用户账户采用下述不可恢复删除语义并保留最小历史身份。

## 2. 模块设计与 seam

M02 是账号和门店身份的权威模块。其他模块只消费稳定的当前用户范围或门店引用，不自行解释角色、复制账号门店绑定，或信任客户端传入的普通用户 `storeId`。

```text
AccountDirectory
  authenticateLookup(username) -> AccountCredentialView       // 仅供 M01
  getActorScope(userId) -> ActorScope
  createAccount(command) -> UserView
  updateAccount(command) -> UserView
  updateOwnProfile(command) -> UserView
  deleteAccount(command) -> void
  resetPassword(command) -> void

StoreDirectory
  requireActiveStore(storeId) -> StoreReference
  getStore(storeId) -> StoreView
  listActiveOptions() -> StoreOption[]
  createStore(command) -> StoreView
  updateStore(command) -> StoreView
  changeStoreStatus(command) -> StoreView
  deleteEmptyStore(command) -> void

SessionRevocationPort
  revokeAllSessions(userId, reason) -> void                    // 由 M01 实现

StoreUsageProbe
  findReferences(storeId) -> StoreReferenceSummary            // 汇总 M03～M07 等模块引用

AuditEventPort
  publish(event) -> void                                       // 由 M10 消费
```

`ActorScope` 固定输出 `userId, roleCode, storeId?`。对 `USER`，`storeId` 必有值；对 `ADMIN`，`storeId` 必为空。M01 将其放入服务端认证上下文，业务接口每次仍以服务端上下文为准。

HTTP 控制器只调用 M02 应用层用例，不自行拼接角色切换、最后管理员保护、门店停用/删除检查或会话撤销步骤。`StoreUsageProbe` 只返回引用摘要，不向 M02 暴露其他模块的表结构；任一引用检查不可用或结果不完整时，门店删除安全失败。账号删除、角色/门店变化和密码重置只有在会话撤销已被 M01 接受后才报告成功，后续受保护请求仍复核权威账号及认证版本。

## 3. 用户与角色模型

### 3.1 角色与门店绑定基线

以下方案已在第 1 步确认：

1. 仅有固定 `ADMIN`、`USER` 两种角色，不开放自定义角色。
2. `ADMIN` 不绑定门店，具备全局管理范围。
3. `USER` 必须且只能绑定一个启用门店。
4. 同一门店允许绑定多个 `USER`。
5. 普通用户的门店范围只取服务端账号绑定，忽略或拒绝客户端伪造的其他门店。

需要以具体场景验证：管理员创建普通用户时未选门店必须失败；普通用户伪造 A 店账号去请求 B 店数据必须返回 403；管理员处理业务时需要显式选择目标门店，不能依赖隐含默认门店。

### 3.2 用户账户生命周期（第 2 步已确认）

- 用户不设置 `ACTIVE/DISABLED` 等业务状态；未删除且绑定规则有效的账户即可登录。
- 管理员可以注册 `ADMIN` 管理员账户，也可以注册 `USER` 普通用户账户；创建时直接确定角色并执行对应的门店绑定校验。
- 管理员可以删除 `USER` 普通用户账户，也可以注销自己或另一个 `ADMIN` 管理员账户。
- 系统始终必须保留至少一个管理员账户，因此最后一个管理员不能注销，也不能改成普通用户。
- 删除或注销立即使目标账户全部已有会话失效，并移除其登录能力、当前账号门店绑定和用户管理列表可见性；管理员注销自己后当前会话立即结束。
- 删除或注销不可恢复，不提供“重新启用”操作；如需再次使用，应由管理员创建新账户。
- 为保证历史导入、销售与审计可解释，内部保留不可登录的最小历史身份以及原始记录引用；这不是可切换的用户状态，也不出现在用户管理列表中。
- 已删除账户的用户名永久保留，不允许新账户复用，避免历史操作人与新账户混淆。

### 3.3 角色切换与门店改绑（第 2 步已确认）

- `ADMIN → USER`：必须同时提交一个启用门店，否则拒绝。
- `USER → ADMIN`：保存成功后清空门店绑定。
- `USER` 改绑门店：只影响改绑后的数据范围；历史导入和审计仍归属原门店，不迁移历史数据。
- 角色变化或门店改绑成功后，使该用户所有已有会话失效，下一次登录获取新范围。
- 不能把系统最后一个管理员改为普通用户，确保系统始终保留至少一个管理员账户。
- 更新使用 `expectedVersion` 乐观锁，防止两个管理员互相覆盖角色或门店绑定。

### 3.4 用户名、个人资料与密码（第 3 步已确认）

- 用户名去除首尾空白后统一转为小写保存和匹配，全局唯一且创建后不可修改；账户删除或注销后也永久保留，不允许复用。
- 用户名推荐为 4～32 位，以英文字母开头，其余允许英文字母、数字、点、下划线和连字符；不允许中文、空格或其他符号。
- 显示名称与登录用户名分离，推荐 1～50 个字符，允许中文，可由管理员修改。
- 管理员和普通用户都可以在“我的资料”中编辑本人姓名、性别、年龄和入职日期；不能借此修改用户名、角色、绑定门店或密码。
- 姓名沿用 API 字段 `displayName`；性别推荐为 `MALE | FEMALE | UNSPECIFIED`；年龄 `age` 直接保存用户手工填写的当前周岁，推荐为可选整数且范围 16～100；入职日期 `hireDate` 使用 `YYYY-MM-DD`，推荐不晚于当天。
- 系统不保存出生日期，也不随时间自动增加年龄；资料所有者或管理员需要在年龄变化后手工更新。
- 管理员也可以通过用户管理页编辑任一未删除账户的上述个人资料字段。
- 只有管理员可以在创建账户时设置初始密码，或通过 API-018 重置任一管理员/普通用户的密码；普通用户不能修改自己的密码，首版不提供找回密码。
- 管理员可以重置自己的密码；重置成功后目标账户全部已有会话失效，因此重置自己时当前会话也立即结束，需要使用新密码重新登录。
- 密码只接受明文请求并立即单向哈希，不写日志、不返回、不持久化明文；具体长度、字符及防爆破规则统一引用 M01 的最终确认结果，不在 M02 维护第二套策略。
- 首版不要求首次登录强制改密，不设置密码有效期或密码历史；如员工忘记密码，由管理员直接重置。

## 4. 门店模型

### 4.1 门店状态（已确认）

```text
StoreStatus = ACTIVE | DISABLED
```

- 门店支持物理删除，但只用于尚未投入使用、没有任何账号或业务数据引用的空门店。
- `DISABLED` 门店不再出现在新建账号、账号改绑和新业务操作的可选门店中。
- 已停用门店的历史数据仍可由管理员查询，不因停用被清空或迁移。

### 4.2 门店停用条件（已确认）

推荐规则：存在尚未删除的普通用户账户时拒绝停用门店；管理员必须先将这些用户改绑或删除。存在历史业务数据不阻止停用，历史数据继续保留原门店引用。

门店停用与用户删除是两个独立操作，M02 不静默批量删除账号。若并发发生门店停用和账号绑定，事务提交时再次校验门店状态。

### 4.3 门店物理删除条件（已确认）

- 只允许物理删除已经处于 `DISABLED` 状态的门店；启用门店必须先停用，避免误触直接删除。
- 删除时必须同时满足：没有尚未删除的普通用户绑定，且没有任何主数据或业务数据引用。引用包括但不限于门店商品、供应商关系、售价、库存、导入批次、库存快照/同步/告警、销售事实、分析配置和其他业务记录。
- 任一历史或当前业务引用存在时拒绝删除，门店只能保持停用；系统绝不通过删除门店级联清空、迁移或改写这些记录。
- 审计事件保存门店 ID、编码、名称及删除结果快照，不以数据库外键反向阻止删除。
- 删除操作在事务提交前再次检查门店状态、账号绑定和业务引用；并发产生新引用时，删除失败且原门店保留。
- 删除成功后，门店从列表、选项和详情中消失，按该 ID 查询返回 `STORE_NOT_FOUND`。门店编码能否复用留到第 5 步字段与唯一性确认。

### 4.4 门店字段（已确认）

```text
StoreView
  id, code, name, address?, contactName?, contactPhone?,
  status, userCount, version, createdAt, updatedAt
```

推荐规则：

- `code`：去除首尾空白并转为大写，按 `[A-Z][A-Z0-9-]{1,31}` 校验；在现存门店中全局唯一，创建后不可修改。物理删除只允许空门店，因此删除成功后该编码可以重新使用，新门店仍取得新的内部 `id`。
- `name`：去除首尾空白后必填，1～100 个字符；允许不同门店重名，名称不作为业务主键或唯一匹配条件。
- `address`：可选，最多 255 个字符。
- `contactName`：可选，最多 50 个字符。
- `contactPhone`：可选，去除首尾空白后最多 30 个字符，按字符串原样保存；不强制手机号格式，以兼容座机、分机和国际区号，但拒绝控制字符。
- 可选文本字段提交空白字符串时统一保存为 `null`。API-024 可编辑名称、地址、联系人和联系电话；内部 `id`、门店编码和创建时间不可编辑，状态只通过 API-025 修改。
- 业务数据只引用不可变内部 `id`；展示使用 `code + name`。

## 5. 权限矩阵（已确认）

| 能力 | 管理员 | 普通用户 |
|---|---|---|
| 查询用户列表/详情 | 未删除账户 | 否 |
| 创建、编辑用户 | 是，受保护规则约束 | 否 |
| 删除普通用户账户 | 是 | 否 |
| 注销管理员账户 | 是；注销后必须仍有其他管理员 | 否 |
| 管理员重置用户密码 | 是 | 否 |
| 编辑本人姓名、性别、年龄、入职日期 | 是 | 是 |
| 查询门店列表/详情 | 全部 | 否；本人门店摘要从 M01 `/auth/me` 获取 |
| 创建、编辑、启停、物理删除空门店 | 是 | 否 |
| 获取启用门店选项 | 是 | 否 |

所有 `/admin/**` 接口由后端独立校验 `ADMIN`；前端隐藏菜单和按钮不构成安全边界。

API-019 的目标用户 ID 只能来自当前认证主体，路径和请求体均不接受其他 `userId`。管理员修改他人资料必须使用 API-016；普通用户不能借个人资料接口改变角色、门店、用户名、密码或其他账户。

```text
CreateStoreRequest
  code, name, address?, contactName?, contactPhone?

UpdateStoreRequest
  name, address?, contactName?, contactPhone?, expectedVersion

ChangeStoreStatusRequest
  status, expectedVersion
```

## 8. 查询、校验、幂等与并发（已确认）

- 列表页 `page` 从 1 开始，`size` 默认 20、最大 100；稳定排序默认为 `createdAt DESC, id DESC`。
- 分页响应统一为 `PageResult<T> { items, page, size, total }`；无匹配记录时 `items=[]`、`total=0`，不返回 404。
- 用户 `keyword` 匹配用户名或显示名；门店 `keyword` 匹配门店编码或名称。
- API-013 支持 `keyword, roleCode, storeId, page, size`；API-020 支持 `keyword, status, page, size`；API-021 不分页且只返回 `ACTIVE` 门店。
- API-019 只更新个人资料，不改变认证版本、不撤销会话；保存后 API-012 返回最新资料。
- 创建请求不通过幂等键自动合并；用户名或门店编码冲突返回明确 409。
- API-015、API-023 创建成功返回 201 和完整视图；API-016、API-019、API-024、API-025 更新成功返回 200 和最新视图；API-017、API-018、API-026 成功返回 204。
- 新建门店默认状态为 `ACTIVE`；创建请求不接受状态字段，后续仅通过 API-025 启停。
- 更新、状态变更和密码重置在请求体提交 `expectedVersion`；API-017、API-026 通过 `If-Match` 请求头提交版本。版本缺失或不一致返回 409，原数据不变。
- 账户或门店首次删除成功返回 204；同一目标的删除请求因网络重试再次到达时，若可从删除记录确认同一目标已成功删除，则仍返回 204 且不重复审计；从未存在的 ID 返回 404。若账户操作会注销最后一个管理员，则返回 409，原账户不变。
- 门店删除不是级联操作；服务端在同一事务中复核门店已停用且无账号或业务引用，任一条件不满足都完整拒绝。
- 创建用户、角色/门店变更、删除用户和重置密码的账号写入与会话失效信号必须保持一致；具体事务/outbox 形态到工程阶段确定。

## 9. 审计与敏感信息（已确认）

建议记录：

- 管理员/普通用户账户创建、角色变化、门店改绑、普通用户删除、管理员注销、管理员重置密码。
- 门店创建、资料修改、启用/停用、物理删除尝试与结果。
- 成功操作，以及 `LAST_ADMIN_REQUIRED`、`STORE_HAS_USERS`、`STORE_IN_USE` 等重要业务规则拒绝；普通字段格式校验失败不逐条写业务审计。
- 操作人、目标 ID、动作、结果、时间、请求追踪号，以及角色、账号门店绑定、门店状态和非敏感资料的变更前后摘要。门店删除审计额外保存删除前的 ID、编码和名称快照。

禁止记录：

- 明文密码、密码哈希、会话标识、Redis 会话值、完整请求体。
- 密码创建/重置摘要中的密码或强度细节；只记录“密码已设置/重置”和结果。

管理员不能通过本模块查询密码、会话标识或账号认证秘密。M10 只消费脱敏后的审计事件。

安全边界：

- 所有接口复用 M01 的服务端会话；所有状态变更请求继续执行 M01 已确认的 CSRF Token 与 Origin 校验。
- 请求 DTO 采用字段白名单，拒绝客户端提交 `passwordHash`、认证版本、审计操作者、内部删除标记等服务端字段。
- 密码明文只在创建或重置请求的必要处理周期内存在，立即交给已确认的 bcrypt 编码器，禁止进入响应、异常详情、日志、追踪标签或审计事件。
- 普通用户数据范围只取当前认证主体的 `storeId`；管理员接口也不信任客户端角色。认证失败与登录失败继续使用 M01 的统一响应，不由 M02 暴露账号是否存在或已删除。

## 10. 错误码（已确认）

| HTTP | `code` | 场景 |
|---:|---|---|
| 400 | `USER_STORE_REQUIRED` | `USER` 未绑定门店 |
| 400 | `ADMIN_STORE_NOT_ALLOWED` | `ADMIN` 提交了门店绑定 |
| 400 | `PASSWORD_POLICY_VIOLATION` | 新密码不满足已确认策略 |
| 403 | `FORBIDDEN` | 非管理员访问管理接口或越权门店范围 |
| 404 | `USER_NOT_FOUND` | 用户不存在 |
| 404 | `STORE_NOT_FOUND` | 门店不存在 |
| 409 | `USERNAME_ALREADY_EXISTS` | 用户名已存在 |
| 409 | `STORE_CODE_ALREADY_EXISTS` | 门店编码已存在 |
| 409 | `STORE_DISABLED` | 创建/改绑用户或新业务操作命中停用门店 |
| 409 | `STORE_HAS_USERS` | 停用门店时仍有未删除普通用户 |
| 409 | `STORE_DELETE_REQUIRES_DISABLED` | 尝试物理删除仍处于启用状态的门店 |
| 409 | `STORE_IN_USE` | 门店仍有账号绑定或主数据/业务数据引用，不能物理删除 |
| 409 | `LAST_ADMIN_REQUIRED` | 注销或角色转换会导致系统没有管理员 |
| 409 | `VERSION_CONFLICT` | 乐观锁版本冲突 |

删除账户或停用门店导致的登录失败必须服从 M01 的统一失败响应，不由 M02 单独泄露账号是否存在、是否已删除或门店状态。

## 11. 前端页面（已确认）

### 11.1 用户管理页

- 筛选：关键字、角色、门店。
- 列表：用户名、显示名、角色、绑定门店、最后登录时间、更新时间。
- 用户详情支持查看完整个人资料；管理员可从详情编辑姓名、性别、手工年龄、入职日期、角色和门店绑定，并可执行删除普通用户、注销管理员或重置密码。
- 表单根据角色联动：选择 `USER` 时门店必选且只显示启用门店；选择 `ADMIN` 时清空并禁用门店字段。
- 普通用户账户显示“删除”，管理员账户显示“注销”；最后一个管理员不允许注销。当前管理员注销自己成功后清除本地会话并返回登录页；前端限制之外，后端仍独立校验。
- 管理员重置自己的密码成功后同样清除当前会话并返回登录页；重置他人密码后留在详情页并提示目标用户需重新登录。

### 11.2 门店管理页

- 筛选：关键字、状态。
- 列表：编码、名称、状态、关联账户数、更新时间。
- 操作：新建、编辑、启停、删除；门店编码创建后只读。
- 停用前展示关联用户数量；存在未删除普通用户时提示先改绑或删除用户。
- 删除按钮只对已停用门店展示；确认框说明不可恢复且不会级联清理。提交后若返回 `STORE_IN_USE`，页面提示“该门店已有引用，只能停用，不能删除”，不另设前端预检查接口或级联清理入口。

### 11.3 我的资料页

- 管理员和普通用户均可查看并编辑本人姓名、性别、年龄和入职日期。
- 年龄由用户直接填写并保存，页面提示“年龄不会自动更新”；不采集出生日期。
- 用户名、角色和绑定门店只读；密码不在此页修改。
- 保存遇到版本冲突时不覆盖他人修改，提示刷新后重新编辑。

| 创建管理员并提交门店 | 拒绝，管理员门店必须为空 |

| 创建普通用户选择停用门店 | 拒绝，不产生用户 |
| 一个门店创建多个普通用户 | 全部成功，各自唯一绑定该门店 |
| 普通用户伪造其他 `storeId` | 后端返回 403，不泄露目标门店数据 |
| 普通用户访问用户/门店管理接口 | 后端返回 403 |
| 管理员删除普通用户 | 删除成功，账户立即不能登录且全部旧会话失效 |
| 管理员创建管理员账户 | 成功，新管理员不绑定门店且可登录 |
| 管理员注销另一个管理员 | 系统仍有其他管理员时成功，目标账户立即不能登录 |
| 管理员注销自己 | 系统仍有其他管理员时成功，当前会话立即结束并返回登录页 |
| 注销或转换最后一个管理员 | 拒绝，原账户保持可用 |
| 管理员重置他人密码 | 新密码可登录，旧密码和旧会话失效 |
| 管理员重置自己的密码 | 成功后当前及其他会话全部失效，页面返回登录页 |
| 普通用户编辑本人资料 | 姓名、性别、手工年龄和入职日期更新成功；角色与门店不变，会话保持有效 |
| 普通用户在本人资料请求中伪造角色或门店 | 字段不被接受，权限范围不变 |
| 普通用户尝试指定其他用户 ID 编辑资料 | 后端拒绝或忽略该字段，其他用户资料不变 |
| 年龄、入职日期或用户名格式非法 | 返回明确校验错误，原数据不变 |
| 删除或注销有历史业务记录的账户 | 用户列表不再显示且不可恢复，历史记录仍可识别原操作人 |
| 用已删除用户名创建新账户 | 拒绝，避免历史身份混淆 |
| 用户角色或门店改变 | 历史记录不迁移，旧会话失效，重新登录后范围更新 |
| 会话撤销未被 M01 接受 | 账号敏感变更不报告成功，不出现“变更成功但旧会话继续有效” |
| 停用含未删除用户的门店 | 拒绝，并返回关联用户数量 |
| 停用含历史业务但无未删除用户的门店 | 成功，历史数据保留且管理员可查 |
| 创建两个同名、不同编码门店 | 均成功；门店名称不作为唯一条件 |
| 创建重复编码或修改既有门店编码 | 重复编码被拒绝；更新接口不接受编码字段 |
| 删除空门店后复用编码 | 新门店创建成功但获得新的内部 ID |
| 物理删除启用门店 | 拒绝，必须先停用 |
| 物理删除已停用且完全无引用的空门店 | 成功，列表和详情均不可再查询该门店 |
| 物理删除仍有账号或任一业务数据引用的门店 | 拒绝，不级联删除任何数据，门店继续保持停用 |
| 门店引用探针不可用或结果不完整 | 删除失败，门店及全部数据保持不变 |
| 删除检查期间并发产生门店引用 | 删除失败，门店及新引用均保持完整 |
| 并发编辑同一用户或门店 | 后提交的旧版本请求返回 409，不覆盖新值 |
| DELETE 缺少/使用过期 `If-Match` | 返回 409，不删除目标；成功请求网络重试返回 204 且不重复审计 |
| 列表无匹配记录 | 返回 200、空 `items` 和 `total=0`，不返回 404 |
| 普通用户伪造 CSRF 或 Origin | 写请求被拒绝，资料和业务范围不变 |
| 响应与审计检查 | 不含密码哈希、明文密码、会话标识或完整请求体 |
